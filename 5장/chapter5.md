# 프로듀서의 기본 역할
- 소스에 있는 메시지들을 카프카의 토픽으로 전송하는 것
- 메시지 : 프로듀서 send() -> 시리얼라이저 -> 파티셔너 -> 카프카
## 5.1 파티셔너
- 카프카 토픽 : 최소 하나 또는 둘 이상의 파티션으로 구성
    - 성능 향상을 위한 병렬 처리가 가능하도록
- 파티셔너 : 프로듀서가 메시지를 어느 파티션으로 보낼지 결정할 때 사용
    - 기본적으로 메시지(레코드)의 키를 해시(hash) 처리해 파티션을 구하는 방식을 사용
    - 메시지의 키값이 동일하면 모두 같은 파티션으로 전송됨
> ## **파티션 vs 파티셔너**
> **파티션: 데이터가 실제로 저장되는 물리적 단위**
- 토픽을 나누는 저장 단위
- 브로커의 디스크에 실제 로그 파일로 존재
- 병렬 처리와 확장성을 위한 구조
> **파티셔너: 메시지를 어느 파티션으로 보낼지 결정하는 로직**
- 프로듀서 측에서 동작하는 알고리즘
- 기본 파티셔너 동작
- 키가 있는 경우: hash 처리하여 파티션을 구함
- 키가 없는 경우: 라운드로빈 또는 스티키 방식으로 파티션 선택
> ***파티션이 데이터가 저장되는 "서랍"이라면, 파티셔너는 어느 "서랍"에 넣을지 결정하는 "분류 규칙"***
### 5.1.1 라운드 로빈 전략
- 메시지 도착 순서대로 파티션을 순환
#### 문제점
- 메시지마다 파티션을 바꿔가며 전송
- 작은 배치들이 여러 파티션으로 분산
- 네트워크 요청 횟수 증가 -> 성능 저하
- 지연시간이 불필요하게 증가
### 5.1.2 스티키 파티셔닝 전략
- `Apache Kafka 2.4 버전(2019년 출시)` 부터는 **스티키 파티셔닝 전략** 사용
- 하나의 파티션에 레코드 수를 먼저 채워서 카프카로 빠르게 배치전송하는 전략
- 라운드 로빈 방식에 비해 약 30% 이상의 지연 시간 감소, 프로듀서의 CPU 사용률 감소 효과

## 5.2 프로듀서의 배치
- 처리량을 높이기 위해 **배치 전송** 권장
- 한 번에 다량의 메시지를 묶어서 전송하는 방법
- 불필요한 I/O를 줄일 수 있어 매우 효율적이며, 카프카의 요청 수를 줄여주는 효과
- 배치 전송을 위한 옵션
    - `buffer.memory`: 프로듀서의 버퍼 메모리 옵션 (기본값: 32MB)
    - `batch.size`: 배치 크기 옵션 (기본값: 16KB)
    - `linger.ms`: 버퍼 메모리에서 대기하는 메시지들의 최대 대기시간 (기본값: 0ms(즉시 전송))
- 처리량(throughput)을 높이려면 `batch.size`와 `linger.ms`를 크게 설정
- 지연(latency) 없는 전송을 하려면 `batch.size`와 `linger.ms`의 값을 작게 설정

> 압축 포맷
> - 높은 압축률 : gzip, zstd
> - 낮은 지연시간 : lz4, snappy

## 5.3 중복 없는 전송
- 적어도 한 번 전송(at-least-once)
    - 네트워크의 회선 장애나 기타 장애 상황에 따라 일부 메시지 중복이 발생할 수는 있지만, 최소한 하나의 메시지는 반드시 보장한다.
    - 메시지 손실 가능성은 없지만, 메시지 중복 가능성 존재
- 최대 한 번 전송(at-most-once)
    - ACK를 받지 못하더라도 재전송 하지 않는다.
    - 메시지의 손실 가능성은 있지만 메시지 중복 가능성은 없음.
    - 높은 처리량을 필요로 하는 대량의 로그 수집 또는 IoT 환경에서 사용
- 중복 없는 전송
    - 카프카 0.11 버전에서 추가됨
    - PID, 메시지 번호
        - PID : 프로듀서에 의해 자동 생성. 프로듀서와 카프카 사이에서 내부적으로만 이용. 사용자에게 노출되지 않음
        - 메시지 번호 : 시퀀스 번호. 0부터 시작해 순차적으로 증가
    - ⭐️ 브로커에서도 기록되는 메시지들에 대해 시퀀스 번호를 증가시킨다. 따라서 프로듀서가 보낸 메시지의 시퀀스 번호가 브로커가 갖고 있는 시퀀스 번호보다 정확하게 하나 큰 경우가 아니라면, 브로커는 프로듀서의 메시지를 저장하지 않는다.
    - 프로듀서 설정
        - `enable.idempotence: true` 중복 없는 전송 허용 여부(기본값: false)
        - `max.in.flight.requests.per.connection: 1~5` ACK를 받지 않은 상태에서 하나의 커넥션에서 보낼 수 있는 최대 요청 수. 5이하로 설정해야 함. (기본값: 5)
        - `acks: all` all 로 설정해야 함. (기본값: 1)
        - `retries: 5` 0보다 큰 값으로 설정해야 함
## 5.4 정확히 한 번 전송
- 카프카에서 '정확히 한 번 전송'은 트랜잭션과 같은 전체적인 프로세스 처리를 의미하며, 중복 없는 전송은 '정확히 한 번 전송'의 일부 기능이라 할 수 있다.
- 트랜잭션API: 전체적인 프로세스를 관리하기 위해 카프카에서 정확히 한 번 처리를 담당하는 별도의 프로세스
### 5.4.1 디자인
- 트랜잭션 코디네이터(transaction coordinator)
    - 프로듀서에 의해 전송된 메시지를 관리하며, 커밋 또는 중단 등을 표시
    - 트랜잭션 로그를 카프카의 내부 토픽(transaction_state)에 저장
    - *프로듀서는 트랜잭션 관련 정보를 트랜잭션 코디네이터에게 알리고, 모든 정보의 로그는 트랜잭션 코디네이터가 직접 기록*
### 5.4.2 프로듀서 예제 코드
### 5.4.3 단계별 동작
#### 1. 트랜잭션 코디네이터 찾기
- **트랜잭션 코디네이터의 주 역할**:
  PID(Producer ID)와 transactional.id를 매핑하고 해당 트랜잭션 전체를 관리하는 것
* 프로듀서는 브로커에게 `FindCoordinator Request`를 보내 트랜잭션 코디네이터의 위치를 찾는다.
  (트랜잭션 코디네이터는 브로커에 위치함)
* 만약 트랜잭션 코디네이터가 존재하지 않으면 신규 트랜잭션 코디네이터가 생성됨
* `__transaction_state` 토픽의 파티션 번호는 `transactional.id`를 기반으로 해시하여 결정되고, 이 파티션의 리더가 있는 브로커가 트랜잭션 코디네이터의 브로커로 최종 선정됨
  -> 이는 `transactional.id`가 정확히 하나의 코디네이터만 갖고 있다는 의미

>**트랜잭션 코디네이터**
>카프카 브로커에서 실행되는 특수한 컴포넌트로, 프로듀서의 트랜잭션 상태를 관리하고 조율하는 역할을 함.


> 1. 트랜잭션 상태 관리
     > 	- 각 `transactional.id`에 대한 트랜잭션 메타데이터 관리
> 	- 트랜잭션의 현재 상태 추적(Ongoing, PrepareCommit, CompleteCommit 등)
> 	- 트랜잭션에 포함된 토픽 파티션 목록 기록
> 2. PID(Producer ID) 할당
     > 	- 프로듀서가 `initTransactions()`를 호출하면 고유한 PID 발급
> 	- `transactional.id`와 PID 매핑 관리
> 	- 프로듀서 재시작 시에도 동일한 `transactional.id`로 새 PID 발급
> 3. 트랜잭션 로그 관리
     > 	- 내부 토픽 `__transactin_state`에 트랜잭션 상태 저장
> 	- 50개 파티션으로 구성 (기본값)
> 	- `transactional.id`를 해싱하여 담당 코디네이터 결정

#### 2. 프로듀서 초기화
- 프로듀서는 `initTransactions()` 메소드를 이용해 트랜잭션 전송을 위한 `InitPidRequest`를 트랜잭션 코디네이터로 보낸다. TID(`transactional.id`)가 설정된 경우에는 TID도 함께 전송됨
- 트랜잭션 코디네이터는 TID, PID를 매핑하고 해당 정보를 트랜잭션 로그에 기록한다.
- PID 에포크를 한 단계 올린다.
#### 3. 트랜잭션 시작
- 프로듀서는 `beginTransaction()` 메소드를 이용해 새로운 트랜잭션의 시작을 알린다.
- 프로듀서는 트랜잭션이 시작됐음을 내부적으로 기록, 하지만 트랜잭션 코디네이터 관점에서는 첫 번째 레코드가 전송될 때까지 트랜잭션이 시작된 것은 아님.
#### 4. 트랜잭션 상태 추가
- 프로듀서는 토픽 파티션 정보를 트랜잭션 코디네이터에게 전달하고, 트랜잭션 코디네이터는 해당 정보를 트랜잭션 로그에 기록한다. (TID, PID 정보, 트랜잭션의 현재상태: Ongoing)
- 만약 트랜잭션 로그에 추가되는 첫 번째 파티션이라면, 트랜잭션 코디네이터는 해당 트랜잭션에 대한 타이머를 시작한다. 기본값으로 1분 동안 트랜잭션 상태에 대한 업데이트가 없다면, 해당 트랜잭션은 실패 처리
#### 5. 메시지 전송
- 프로듀서는 대상 토픽의 파티션으로 메시지(PID, 에포크, 시퀀스 번호 포함)를 전송한다.
#### 6. 트랜잭션 종료 요청
- 프로듀서는 `commitTransaction()`메소드 또는 `abortTransaction()`메소드 중 하나를 반드시 호출해야 하며, 해당 메소드의 호출을 통해 트랜잭션이 완료됨을 트랜잭션 코디네이터에게 알린다.
- 트랜잭션 코디네이터는 2단계의 커밋(2PC)과정을 시작한다.
    - 첫 번째 단계: 트랜잭션 로그에 해당 트랜잭션에 대한 PrepareCommit 또는 PrepareAbort 기록
    - 두 번째 단계: 사용자 토픽에 표시. 트랜잭션 코디네이터는 트랜잭션 로그에 기록된 토픽의 파티션에 트랜잭션 커밋 표시(컨트롤 메시지)를 기록한다.

>**2단계 커밋 프로토콜 (2PC)**
>Prepare 단계:
> - 코디네이터가 트랜잭션 로그에 "PrepareCommit" 상태 기록
> - 이 시점부터 트랜잭션은 커밋되어야 함
    >Commit 단계:
> - 관련된 모든 데이터 파티션에 트랜잭션 마커 기록
> - 마커는 컨슈머에게 메시지 가시성을 제어
> - 모든 마커 기록 완료 후 "CompleteCommit" 상태로 전환
#### 7. 트랜잭션 완료
- 트랜잭션 코디네이터는 완료됨(Committed)이라고 트랜잭션 로그에 기록한다.
- 그리고 프로듀서에게 해당 트랜잭션이 완료됨을 알린다.
- 트랜잭션을 이용하는 컨슈머는 `read_committed` 설정을 하면 트랜잭션에 성공한 메시지들만 읽을 수 있다.

>**트랜잭션 처리 흐름**
>1. 프로듀서 초기화
    >   프로듀서 -> 코디네이터 : `InitProducerId` 요청
    >   코디네이터 -> 프로듀서 : PID 발급
>2. 트랜잭션 시작
    >   프로듀서 -> 코디네이터 : `AddPartitionsToTxn` (참여 파티션 등록)
>3. 메시지 전송
    >   프로듀서 -> 브로커 : 데이터 파티션에 메시지 전송
>4. 트랜잭션 커밋
    >   프로듀서 -> 코디네이터 : EndTxn (COMMIT)
    >   코디네이터 -> 브로커 : 각 파티션에 트랜잭션 마커 기록
    >   코디네이터 : 트랜잭션 상태를 완료로 업데이트
